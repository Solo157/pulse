## 1. Цель

Pulse — демонстрационная платформа мониторинга приложений. Она принимает метрики клиентов, асинхронно сохраняет исторические точки, анализирует значения по правилам, регистрирует инциденты и создаёт уведомления.

Главная цель DEMO — продемонстрировать преподавателю не только работу приложения, но и:
- нагрузку и фактическую пропускную способность;
- горизонтальное масштабирование сервисов;
- балансировку пользовательских запросов;
- поведение при отказе отдельных экземпляров и зависимостей;
- накопление сообщений в Kafka во время недоступности потребителей/хранилища;
- восстановление компонентов и разбор накопившейся очереди;
- влияние отказов на HTTP errors и latency;
- наблюдаемость всех экспериментов через Prometheus и Grafana.

Во время экспериментов генератор нагрузки должен продолжать отправлять запросы. Нужно измерять, какие запросы успешны, какие завершились ошибкой, как изменились задержки, очереди и время восстановления. Нельзя утверждать, что пользователь «ничего не заметил», если тест показывает ошибки или значительный рост latency.

Docker Compose на одной машине не обеспечивает production availability 99,99%. Нужно различать отказоустойчивость приложения и отказоустойчивость физической инфраструктуры.

## 4. Функциональные требования

### FR-1. Регистрация
Клиент регистрируется и получает идентификатор и API key для отправки метрик и чтения своих данных. Регистрация автоматически включает клиента в получение уведомлений, как указано в презентации.

Для DEMO допустима упрощённая аутентификация по API key. Полноценный OAuth2/JWT и сложные роли не требуются без отдельного согласования.

### FR-2. Приём метрик
Клиент отправляет пакет MetricPoint одним HTTP-запросом. MetricService валидирует запрос, публикует событие в Kafka и возвращает `202 Accepted` после подтверждения публикации брокером. Это означает, что данные приняты для дальнейшей обработки, а не обязательно уже записаны в ClickHouse.

Пример payload (окончательный контракт согласовать):

```json
{
  "metrics": [
    {
      "name": "cpu_usage",
      "value": 75.5,
      "timestamp": "2026-11-05T10:15:30Z"
    }
  ]
}
```

### FR-3. История метрик
Клиент получает исторические точки своей метрики из ClickHouse за указанный диапазон времени. Нужны лимиты диапазона/размера выдачи. Нельзя читать данные другого пользователя.

### FR-4. История инцидентов
Клиент получает список своих инцидентов за период из PostgreSQL.

### FR-5. Уведомления
При нарушении MonitoringRule создаётся событие `IncidentDetected`. NotificationService получает его, сохраняет Notification и выполняет демонстрационную доставку. Реальную почтовую инфраструктуру подключать только после согласования. Демонстрационная доставка должна быть реальным проверяемым этапом с зафиксированным статусом, а не пустой заглушкой.

## 5. Нагрузка и NFR

Ориентиры из презентации:

| Показатель | Значение |
|---|---:|
| Обычная обработка | 20 000 points/s |
| Пиковая обработка | до 60 000 points/s |
| HTTP RPS при batch 100 точек | 200 обычно |
| HTTP RPS при batch 100 точек | 600 пик |
| Доступность данных после подтверждения | до 5 секунд |
| Обнаружение инцидента обычно | до 10 секунд |
| Обнаружение инцидента на пике | до 20 секунд |
| Ограничение HTTP-запроса | ориентир до 100 КБ |

RPS зависит от batch size. 20k/60k points/s — это не HTTP RPS. 200/600 RPS рассчитаны при допущении 100 точек в одном запросе. Генератор должен позволять менять batch size и интенсивность.

Это целевые ориентиры, а не гарантия производительности Compose на любой машине. Агент должен измерить реальную пропускную способность стенда и не выдавать плановые значения за достигнутые.

Требования: отсутствие постоянного роста Kafka Consumer Lag при нагрузке, которую стенд способен обрабатывать; горизонтальное масштабирование stateless-сервисов; независимое масштабирование consumer groups; асинхронная обработка; retry и идемпотентность; eventual consistency; измерение фактических задержек и ошибок.

## 6. Архитектура и компоненты

Следовать окончательной презентации и схеме. Основной логический поток:

```text
Client
  |
Nginx API Gateway
  |
MetricService (1..N)
  |                         \
PostgreSQL                   Kafka: metrics
                                /           \
                       storage-group   processing-group
                            |                |
                      StorageService   ProcessingService
                            |                |
                        ClickHouse          |
                                             v
                                      Kafka: incidents
                                         /       \
                              notification-group metric-group
                                     |                |
                             NotificationService  MetricService
                                     |                |
                                 PostgreSQL       PostgreSQL
```

### 6.1. Nginx API Gateway
- единая HTTP-точка входа;
- reverse proxy к MetricService;
- балансировка `least_conn`;
- access logs с request id, upstream, status и временем обработки;
- метрики RPS, ошибок, latency, распределения по upstream;
- динамическое обнаружение экземпляров после Compose scale/recreate.

Важно: стандартный OSS Nginx имеет ограничения по активным health checks. Не выдавать пассивное обнаружение ошибок за полноценную активную проверку. Агент должен предложить реализацию динамического Docker DNS/upstream и согласовать её. Не использовать `container_name` для масштабируемых сервисов.

### 6.2. MetricService
- регистрация клиента и выдача/проверка API key;
- приём batch метрик;
- публикация в Kafka `metrics`;
- API чтения истории из ClickHouse;
- API чтения инцидентов из PostgreSQL;
- хранение User, Metric, MonitoringRule;
- consumer group `metric-group` читает `incidents` и сохраняет Incident в PostgreSQL.

HTTP-сервис должен быть stateless и масштабироваться горизонтально.

### 6.3. StorageService
- consumer group `storage-group` читает `metrics`;
- пакетная запись точек в ClickHouse;
- commit offset только после успешной записи;
- retry с backoff при временной недоступности;
- контролируемое поведение при постоянной ошибке (согласовать DLQ/parking lot или остановку partition);
- защита от повторной доставки и дублей.

### 6.4. ProcessingService
- consumer group `processing-group` читает `metrics`;
- получает MonitoringRule;
- анализирует точки;
- публикует `IncidentDetected` в `incidents`;
- обрабатывает повторную доставку;
- не создаёт бесконечный поток одинаковых инцидентов на каждую точку при непрерывном нарушении правила.

Семантику открытия/закрытия инцидента, cooldown и out-of-order событий согласовать до реализации.

### 6.5. NotificationService
- consumer group `notification-group` читает `incidents`;
- создаёт Notification;
- сохраняет статус и количество попыток в PostgreSQL;
- выполняет согласованную демонстрационную доставку;
- retry при временных ошибках;
- идемпотентная обработка.

### 6.6. Kafka
Топики и группы:

| Topic | Producer | Consumer groups |
|---|---|---|
| `metrics` | MetricService | `storage-group`, `processing-group` |
| `incidents` | ProcessingService | `metric-group`, `notification-group` |

Разные consumer groups независимо читают полный поток topic. Consumers внутри одной группы делят partitions. Число реально параллельно работающих consumers ограничено числом partitions.

Kafka message key — `userId`, как в презентации. Это сохраняет порядок сообщений пользователя внутри partition, но может привести к hot partition при неравномерной нагрузке.

Целевая конфигурация из презентации:
- `replication.factor=3`;
- `min.insync.replicas=2`;
- producer `acks=all`;
- `enable.idempotence=true`.

Три брокера на одной VM не защищают от отказа VM. При одном брокере отказ брокера означает недоступность Kafka. Агент должен предложить базовый single-broker режим и отдельный multi-broker Compose profile (если владелец согласует). Количество partitions, retention и consumer concurrency обосновать и согласовать.

### 6.7. PostgreSQL
Бизнесовые данные: User, Metric, MonitoringRule, Incident, Notification (согласно презентации). Нужны миграции, индексы, ограничения уникальности. Один PostgreSQL в базовом DEMO допустим, но является SPOF. HA — отдельное согласуемое расширение.

### 6.8. ClickHouse
Хранит MetricPoint и обслуживает историю временных рядов. Целевая модель презентации: шардинг по `userId`, партиционирование по времени, реплики внутри shard. Для базового локального DEMO допустим один ClickHouse без физического шардинга/репликации, с временным partitioning.

StorageService подтверждает Kafka offset только после успешной вставки. Нужно проверить crash window «вставка прошла, offset не committed»: повторная доставка может вызвать дубль. Предусмотреть consumer idempotency/дедупликацию.

## 7. Идемпотентность

Различать:
1. API idempotency — повтор HTTP с тем же `Idempotency-Key`;
2. Kafka producer idempotence — защита от дублей при producer retries в пределах гарантий Kafka;
3. Consumer idempotency — повторное событие не должно повторно создавать бизнесовый результат.

Producer idempotence не заменяет два остальных механизма. События должны иметь стабильный `eventId`. Не считать схему «publish в Kafka, затем сохранить ключ в Redis» атомарной: между действиями есть crash window. Если нужна надёжная API idempotency, агент должен предложить варианты и спросить владельца. Redis не обязателен.

## 9. API

Ориентироваться на API презентации:

| Метод | Endpoint | Назначение |
|---|---|---|
| POST | `/auth/register` | Регистрация |
| POST | `/users/{userId}/metrics` | Приём batch метрик |
| GET | `/users/{userId}/metrics/{metricName}/history?from={timestamp}&to={timestamp}` | История метрики |
| GET | `/users/{userId}/incidents?from={timestamp}&to={timestamp}` | История инцидентов |

Для ingest: `Idempotency-Key: <unique-request-id>`. API key передавать согласованным заголовком. Проверять, что пользователь не может прочитать чужие данные, подставив `userId`.

- ошибки валидации — понятные 4xx;
- недоступность Kafka не маскировать успешным 202;
- 202 возвращать только после подтверждения публикации;
- история может отставать от ingest до 5 секунд;
- контракты документировать.

События метрик и `IncidentDetected` должны содержать как минимум `eventId`, `userId`, время создания/приёма, версию схемы, данные события и поля корреляции. Имена event types, формат времени, batch size и формат ошибок согласовать до реализации.

## 10. Мониторинговые правила

Для DEMO нужен простой rule, например `temperature > 80` → `IncidentDetected`. До реализации согласовать:
- один инцидент на непрерывный период нарушения или новый на каждую точку;
- условие закрытия инцидента;
- cooldown;
- обработку неупорядоченных точек;
- идентификацию правила.

Не реализовывать сложный rule engine. Правила не должны требовать синхронного запроса к MetricService на каждую точку. Агент предлагает простой механизм хранения/кэширования правил и согласует.

## 11. Масштабирование через Compose

Обязательное:
- MetricService — несколько экземпляров;
- StorageService, ProcessingService, NotificationService — несколько экземпляров одной consumer group;
- Nginx балансирует HTTP между MetricService;
- масштабирование без изменения кода;
- сервисы не хранят критичное состояние локально;
- масштабируемые сервисы без фиксированного `container_name`;
- нет конфликта опубликованных host ports;
- graceful shutdown consumers и корректное перераспределение partitions;
- документированные команды и ограничения Compose.

Ожидаемые команды (уточнить service names под итоговый Compose):

```bash
docker compose up -d --scale metric-service=2
docker compose up -d --scale metric-service=3
docker compose up -d --scale processing-service=2
```

Проверить, что экземпляры действительно созданы, Nginx обнаруживает MetricService, а Kafka распределяет partitions. Число consumers не равно числу параллельных обработчиков: параллелизм ограничен partitions.

## 12. Генератор нагрузки

В проекте должен быть отдельный нагрузочный генератор (не внутри MetricService), запускаемый из Compose или отдельной документированной командой.

Настройки:
- RPS или points/s;
- batch size;
- длительность;
- число виртуальных пользователей/параллельных клиентов;
- набор тестовых пользователей;
- steady, step, burst профили;
- генерация значений, вызывающих MonitoringRule;
- URL Gateway и API key через env.

Инструмент (k6, Gatling, hey и т.п.) агент предлагает и согласует. Сценарии должны быть воспроизводимыми и храниться в репозитории.

Минимальные тесты: smoke, baseline, step load, burst, recovery. Для каждого сохранять параметры, фактические RPS/points/s, успешные/ошибочные HTTP-запросы, p50/p95/p99, отправленные/принятые точки, время появления в ClickHouse, Kafka lag, CPU/RAM и логи.

## 13. Prometheus и Grafana

Prometheus должен собирать метрики приложений через Spring Boot Actuator + Micrometer и метрики инфраструктуры через подходящие exporters. Grafana dashboards автоматически загружаются через provisioning; после запуска не требуется ручной импорт.

### HTTP/Nginx
- RPS;
- запросы по status code;
- 4xx/5xx rate;
- p50/p95/p99 latency;
- активные соединения (если доступны);
- запросы/ошибки по upstream;
- распределение запросов по экземплярам MetricService.

### MetricService
- принятые batch и points;
- отклонённые batch;
- Kafka publish success/failure;
- publish latency;
- HTTP latency/errors;
- instance label.

### Kafka
- incoming/outgoing records и bytes rate;
- consumer lag по каждой группе и topic;
- partitions и распределение consumers;
- producer/consumer errors;
- retry count;
- диск/объём данных, если доступно.

### StorageService/ClickHouse
- скорость чтения и записи;
- persisted points;
- insert latency;
- ошибки и retry;
- batch size;
- время от приёма до появления в ClickHouse;
- доступность ClickHouse.

### ProcessingService
- скорость обработки;
- обработанные точки;
- число инцидентов;
- processing latency;
- ошибки;
- задержка до публикации инцидента;
- consumer lag.

### NotificationService
- полученные IncidentDetected;
- созданные/доставленные уведомления;
- ошибки и retry;
- delivery delay;
- consumer lag.

### JVM/контейнеры
- CPU/RAM;
- JVM heap/non-heap;
- GC;
- threads;
- рестарты и состояние контейнеров.

Не использовать `userId`, `requestId`, `eventId`, `metricName` как Prometheus labels — это создаёт высокую cardinality.

### Dashboards
Обязательно подготовить:
1. **Pulse Overview** — общий статус, RPS, points/s, errors, p95/p99, Kafka lag.
2. **Services / JVM** — экземпляры, CPU/RAM/JVM, рестарты.
3. **Kafka** — throughput, partitions, consumer groups, lag.
4. **Storage** — ClickHouse inserts, errors, latency, points persisted.
5. **Incidents & Notifications** — обнаружение, публикация, доставка, задержки.

Панели должны позволять сопоставить действие и эффект. Например, остановили ProcessingService — lag `processing-group` растёт; запустили — throughput возобновляется, lag уменьшается.

## 14. Сценарии отказоустойчивости

Каждый сценарий оформить в runbook: исходное состояние, нагрузка, команда отказа, время наблюдения, команда восстановления, ожидаемое поведение, панели Grafana, критерии успеха и ограничения. Генератор нагрузки продолжает работать, если это безопасно для конкретного теста.

### FT-1. Остановка одного MetricService
Запустить 2+ экземпляра и нагрузку через Nginx. Остановить один экземпляр. Ожидание: Nginx перестаёт направлять туда новые запросы, оставшиеся экземпляры обслуживают поток, после запуска экземпляр возвращается в upstream.

Наблюдать: RPS/upstream distribution, 5xx, p95/p99, active connections, accepted/rejected batches, CPU/RAM. Зафиксировать ошибки переходного периода.

### FT-2. Масштабирование MetricService
Изменять число экземпляров вверх и вниз во время нагрузки. Наблюдать распределение трафика, throughput, latency, errors и ресурсы. Сравнить результаты до/после; не обещать линейное масштабирование без измерений.

### FT-3. Полная остановка ProcessingService
Остановить все экземпляры во время ingest. Приём метрик и StorageService продолжают работать; `processing-group` lag растёт. После запуска сервисы разбирают backlog, lag уменьшается, инциденты снова обнаруживаются.

Наблюдать: Kafka incoming rate, lag, processing throughput, incidents count, incident delay, HTTP metrics. Проверить отсутствие лишних дублей.

### FT-4. Полная остановка StorageService
Остановить все экземпляры. Ingest продолжается, `storage-group` lag растёт. После восстановления точки записываются в ClickHouse, lag уменьшается. Проверить историю и дубли.

### FT-5. Недоступность ClickHouse
Остановить/замедлить ClickHouse. StorageService не подтверждает offset неуспешно записанных сообщений; retry с backoff; lag растёт. После восстановления вставки продолжаются. Проверить crash window «insert успешен, offset не committed».

### FT-6. Остановка NotificationService
Создавать инциденты, остановить NotificationService. `notification-group` lag растёт. После восстановления создаются и доставляются уведомления. Проверить retry и отсутствие дубликатов.

### FT-7. Пиковая нагрузка
Увеличить поток от обычного профиля до целевого пика 60k points/s и вернуть обратно. Наблюдать фактические points/s, RPS, HTTP errors, p95/p99, CPU/RAM, Kafka lag, insert latency и incident delay. Зафиксировать фактический предел машины и время drain backlog.

### FT-8. Отказ Kafka broker
Возможен только при нескольких брокерах и корректной репликации partitions. С одним брокером остановка означает недоступность Kafka, а не failover. Агент должен предложить владельцу:
- оставить один брокер и задокументировать ограничение;
- добавить multi-broker Compose profile (например, 3 brokers, RF=3, minISR=2) и проверить остановку одного брокера.

Три контейнера на одной VM не защищают от потери хоста.

### FT-9. Отказ PostgreSQL и Nginx
Презентация описывает PostgreSQL primary/replica с автоматическим failover и два Nginx + Keepalived/VRRP. Один контейнер PostgreSQL или один Nginx не могут продемонстрировать такое переключение.

Агент должен спросить владельца, нужны ли расширенные профили:
- PostgreSQL HA с механизмом failover;
- два Gateway и Keepalived/VRRP.

Не выдавать restart контейнера за failover. Keepalived в Docker на одной машине не эквивалентен двум независимым серверам.

## 16. Тестирование

Обязательные уровни:

**Unit:** валидация, правила, преобразование событий, retry, идемпотентность.

**Integration:** MetricService+Kafka; StorageService+Kafka+ClickHouse; ProcessingService+Kafka; NotificationService+Kafka+PostgreSQL. Использовать Testcontainers или согласованный эквивалент. Проверять реальные взаимодействия, не только mocks.

**E2E:** регистрация → ingest → Kafka → ClickHouse → rule → IncidentDetected → PostgreSQL → Notification → чтение истории/инцидентов.

**Fault tests:** воспроизвести сценарии раздела 14 и сохранить результаты.

## 17. Логи и корреляция

Структурированные логи в stdout/stderr. Предусмотреть request/trace id, eventId, имя сервиса/экземпляра, сообщения о retry и ошибках. Не писать секреты в логи. `userId` допустим в логах, но не как Prometheus label.

OpenTelemetry/Tempo/Jaeger можно предложить как дополнительную опцию, если это не вытесняет обязательную функциональность. Минимально обязательны correlation id и метрики.

## 18. Docker Compose

Предусмотреть:
- основной `docker-compose.yml`;
- отдельные compose files/profiles для observability и расширенных HA-экспериментов;
- healthchecks там, где доступны;
- `depends_on` не считать заменой retry/reconnect;
- named volumes для PostgreSQL, Kafka, ClickHouse;
- restart policies;
- конфигурацию через env и `.env.example`;
- инструкции очистки данных/volumes;
- graceful shutdown и переподключение сервисов после временной недоступности зависимостей.

`restart: always`/`unless-stopped` перезапускает процесс, но не обеспечивает failover и не защищает от отказа хоста.

## 19. DEMO и production — не смешивать

В документации явно разделять реально реализованное и проверенное в DEMO от целевой production-архитектуры.

Production-направления презентации:
- Kafka RF=3 на независимых узлах/AZ;
- PostgreSQL primary/replica и автоматический failover;
- ClickHouse shards по userId и replicas;
- ClickHouse Keeper;
- два Nginx + Keepalived/VRRP на независимых хостах;
- backup/restore и проверка восстановления;
- подтверждённый SLO 99,99%.

Compose на одной VM не подтверждает 99,99% и не защищает от отказа VM, диска, Docker Engine или сети хоста.

## 23. Критерии завершения

Pulse DEMO готов, когда:
- Maven multi-module проект собирается;
- Compose поднимает все компоненты;
- регистрация и API key работают;
- MetricService принимает метрики через Nginx;
- `202` возвращается после подтверждения Kafka;
- StorageService сохраняет точки в ClickHouse;
- ProcessingService обнаруживает нарушение правила;
- Incident сохраняется в PostgreSQL;
- NotificationService создаёт и доставляет уведомление;
- клиент читает собственную историю метрик и инцидентов;
- Prometheus собирает метрики, Grafana dashboards загружаются автоматически;
- генератор меняет RPS/points/s и batch size;
- масштабирование MetricService и consumers проверено;
- остановка ProcessingService, StorageService, ClickHouse и NotificationService воспроизводима;
- после восстановления backlog обрабатывается, lag сокращается;
- HTTP errors/latency и внутренние очереди измеряются;
- ограничения стенда задокументированы;
- в корне есть актуальный `result.md`.

**Итог:** не просто набор микросервисов, а воспроизводимый стенд, на котором преподаватель может создавать нагрузку, масштабировать компоненты, отключать их, наблюдать последствия на графиках и видеть восстановление обработки данных.
