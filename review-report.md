# Pulse — технический аудит реализации PR

Дата анализа: 2026-11-08  
Основание: архив `pulse.zip` (снимок репозитория, включая исходники, конфигурацию, тесты и документацию).

## 1. Итоговая оценка

**Вердикт: хорошая основа DEMO, но пока не готово к защите как доказанная высоконагруженная и отказоустойчивая система. Нужны исправления P0 и повторные испытания.**

Реализация уже содержит:
- Maven multi-module: `pulse-contracts`, `metric-service`, `storage-service`, `processing-service`, `notification-service`;
- раздельные контуры приёма, хранения, обработки правил и уведомлений;
- Kafka topics `metrics` и `incidents`, отдельные consumer groups;
- PostgreSQL для пользователей/состояний/инцидентов/уведомлений и ClickHouse для истории метрик;
- Nginx перед `metric-service`, Compose scaling для прикладных сервисов;
- health endpoints, Micrometer/Prometheus, Grafana;
- интеграционные тесты и скрипты fault injection.

Это не пустой каркас: основные пользовательские потоки реализованы. Однако присутствуют риски потери/дублирования событий, а нагрузочные результаты на порядки ниже целевых требований.

### Оценка по направлениям

| Направление | Оценка | Комментарий |
|---|---|---|
| Архитектурное разделение | Хорошо | Сервисы и хранилища разделены по назначению |
| Приём и Kafka | Требует исправления | Есть неопределённый исход publish timeout и окно рассогласования idempotency |
| Запись в ClickHouse | В целом правильно | Offset подтверждается после обработки batch; проверить фактическую дедупликацию и частичные вставки |
| Обработка инцидентов | Критическая проблема | Изменение состояния PostgreSQL выполняется до публикации события |
| Уведомления | Частично | Есть ограниченные синхронные повторы, но терминальный FAILED не переигрывается автоматически |
| Горизонтальное масштабирование | Частично реализовано | Можно масштабировать сервисы, но parallelism ограничен 2 partitions; есть общие узкие места |
| Kafka HA | Ограниченно | Два data brokers + controller-only node; RF=2/minISR=2 не переживает потерю одного broker для записи |
| Nginx | Рабочая DEMO-схема | Один gateway — SPOF; DNS-based балансировка не равна полноценной health-aware least_conn |
| Наблюдаемость | Частично | Нет экспортируемого Kafka consumer lag; не все важные задержки/очереди измеряются |
| Нагрузочные испытания | Недостаточно | Максимум в отчёте — 50 HTTP RPS с одной точкой в запросе, а цель — 20k/60k points/s |
| Fault injection | Хорошая заготовка | Сценарии есть, но некоторые выводы в документах противоречат коду/топологии |
| Production HA | Нет | Один Compose host, единичные PostgreSQL/ClickHouse/Nginx; это честно обозначено как DEMO |

## 2. Критические проблемы — исправить до защиты

### P0-1. Потеря события открытия/закрытия инцидента при ошибке Kafka

Файлы:
- `processing-service/src/main/java/com/pulse/processing/service/IncidentEvaluator.java`
- `processing-service/src/main/java/com/pulse/processing/service/IncidentPublisher.java`

Фактический порядок при открытии:
1. `stateRepository.registerSample(...)`;
2. `stateRepository.openIncident(...)` — PostgreSQL уже фиксирует `open=true`;
3. `publisher.publish(...)` — только теперь отправка в Kafka `incidents`.

Если publish падает/таймаутится, Kafka listener не подтверждает исходное сообщение `metrics` и повторяет обработку. Но повторная обработка увидит `state.open()==true`, вызовет `registerViolation()` и **не повторит публикацию события открытия**. В итоге инцидент может остаться только в `incident_state`, но отсутствовать в `metric.incidents` и `notification.notifications`.

Для закрытия аналогично: `closeIncident()` выполняется до `publisher.publish(close=true)`. При сбое Kafka повторная нормальная точка увидит `open=false`, поэтому событие закрытия не будет опубликовано. История может остаться в статусе OPEN.

Комментарий в `IncidentPublisher` утверждает, что событие публикуется до фиксации состояния, но код `IncidentEvaluator` делает наоборот.

**Это реальный дефект согласованности, не теоретическая рекомендация.** Нужен transactional outbox в PostgreSQL (предпочтительно) либо другая схема, гарантирующая повторную публикацию события после рестарта/ошибки. Простая перестановка вызовов недостаточна: без общей транзакции остаётся окно между Kafka publish и записью состояния.

### P0-2. Неопределённый результат Kafka publish в MetricService + удаление idempotency claim

Файлы:
- `metric-service/src/main/java/com/pulse/metric/service/MetricIngestService.java`
- `metric-service/src/main/java/com/pulse/metric/service/MetricEventPublisher.java`
- `metric-service/src/main/java/com/pulse/metric/repository/IngestIdempotencyRepository.java`

`MetricEventPublisher.publish()` ждёт future максимум `publishAckTimeout` (5 секунд). При `TimeoutException` он возвращает ошибку. Но timeout ожидания **не доказывает, что Kafka не записала событие**: broker мог принять запись, а ack мог задержаться/потеряться.

После любой runtime-ошибки `MetricIngestService` удаляет запись `IN_PROGRESS`. Клиент повторяет тот же ключ, сервис создаёт новую запись и публикует новое событие с новым `eventId`. Первое событие при этом тоже может оказаться в Kafka. Результат — двойная обработка одного пользовательского batch.

Обратное crash window тоже есть: Kafka подтвердила событие, но процесс упал до `markCompleted()`. Запись остаётся `IN_PROGRESS`, повтор клиента получает 409 навсегда (если нет механизма восстановления/lease).

**Нужно:** хранить стабильный идентификатор операции и устойчивое состояние приёма, корректно обрабатывать неопределённый результат. Лучший вариант — transactional outbox для публикации метрик, где создание idempotency claim и outbox record происходит в одной транзакции PostgreSQL, а отдельный publisher доставляет outbox в Kafka. Если outbox сочтут слишком большим объёмом для DEMO, агент должен предложить владельцу варианты и явно описать остаточные гарантии, но не удалять claim после простого timeout.

### P0-3. В нагрузочных тестах не проверяется целевая нагрузка в points/s

Файлы:
- `loadgen.py`
- `docs/results-et7.md`
- `result.md`
- `implementation.md`

Генератор формирует payload с **одной** точкой:
`{"metrics": [{"name": "temperature", ...}]}`.

Поэтому:
- 10 RPS ≈ 10 points/s;
- 40 RPS ≈ 40 points/s;
- 50 RPS ≈ 50 points/s.

Целевые требования — 20 000 points/s обычно и 60 000 points/s на пике. При batch size 100 это около 200/600 HTTP RPS. Текущий тест 50 points/s примерно в 400–1200 раз ниже целей по точкам в секунду. Таблица результатов не подтверждает способность системы выдержать требования преподавателя.

Генератор должен поддерживать `LOAD_BATCH_SIZE`, генерировать batch нужного размера и считать фактически отправленные/принятые **точки**, а не только HTTP-запросы. Нужны тесты с 100 points/request и ступенями по points/s. Если один хост не тянет целевую нагрузку, это нужно честно зафиксировать как предел стенда, а не объявлять требование выполненным.

Также сейчас генератор не фиксирует в итоговом JSON:
- запланированное число запросов/точек;
- фактическую скорость отправки и завершения;
- длину/переполнение очереди генератора;
- throughput по точкам;
- распределение HTTP-кодов;
- p99;
- длительность drain Kafka lag после нагрузки.

### P0-4. Документация завышает/неверно описывает Kafka topology и HA

Файл: `docker-compose.yml`.

Развёрнуто:
- `kafka1`: broker + controller;
- `kafka2`: broker + controller;
- `kafka3`: только controller, без broker listener.

Следовательно, это **2 data brokers + 1 controller-only node**, не 3 брокера. RF=2 означает две копии данных. `min.insync.replicas=2` и `acks=all` означают, что при потере одного из двух брокеров запись остановится. Это подтверждается ожидаемым сценарием F6, но противоречит некоторым формулировкам в комментариях/отчётах о переживании отказа одного брокера.

Для DEMO можно оставить текущую конфигурацию и объяснить её ограничение. Для демонстрации записи при отказе одного broker нужны как минимум 3 data brokers, RF=3, minISR=2, размещённые на независимых узлах. Три контейнера на одной VM не защищают от потери VM.

### P0-5. Доказательства fault injection частично не воспроизводимы/противоречивы

Файлы:
- `docs/fault-injection.md`
- `docs/decisions.md`
- `result.md`
- `scripts/chaos.sh`

В `docs/fault-injection.md` F5 всё ещё описывает GET как зависающий >15 секунд и говорит, что решение только частично закрыто. `result.md`/`docs/decisions.md` описывают уже добавленный TimeLimiter/CircuitBreaker и ответ около 1 секунды. Нужно привести документы к одному актуальному состоянию и повторно прогнать F5 на текущем коде.

В F1 `proxy_next_upstream ... non_idempotent` разрешает Nginx повторять POST после ошибки. Это безопасно только если idempotency действительно корректна на всех crash/timeout paths. Сейчас P0-2 оставляет риск дублей при неопределённом publish result. Нельзя считать повтор POST гарантированно безопасным до исправления идемпотентности.

## 3. Существенные проблемы P1

### P1-1. Обработка инцидента и transactional semantics
Исправить P0-1 через outbox. Дополнительно:
- уникальный business key инцидента не должен приводить к перезаписи истории предыдущих периодов;
- сейчас `IncidentRowRepository.open()` делает `ON CONFLICT (incident_key) DO UPDATE`, то есть один `incident_key` переоткрывает ту же строку. Если FR требует историю инцидентов, это теряет историю отдельных периодов. Нужно согласовать: одна строка на весь lifecycle или отдельная строка на каждый incident occurrence.
- `IncidentDetected.eventId` новый при каждой публикации, поэтому downstream dedup по eventId не предотвращает повторные бизнес-события одного перехода. Нужен стабильный transition/event identity, например incident key + version/transition id.

### P1-2. Consumer parallelism ограничен 2 партициями

Файл: `docker-compose.yml` (`kafka-init` создаёт `metrics` и `incidents` с 2 partitions).

В одной consumer group одновременно активно обрабатывать топик могут максимум два consumer instances. Три и более реплики `storage-service`, `processing-service` или `notification-service` не увеличат параллелизм соответствующей группы при двух partitions. Дополнительные экземпляры будут простаивать.

Для защиты нужно:
- показать scaling до 2 реплик как реально полезный текущий предел;
- измерить распределение partition/lag;
- если нужна демонстрация более чем 2 активных consumers, увеличить partitions заранее и объяснить изменение ordering/partition key;
- число partitions выбирать с учётом максимальной параллельности и будущего роста, а не масштабировать контейнеры без изменения Kafka.

### P1-3. ProcessingService: последовательная обработка и потенциально длинная блокировка партиции

`MetricIncidentListener` вызывает evaluator синхронно; evaluator перебирает все точки и правила, делает JDBC операции и синхронно ждёт Kafka ack для каждого перехода инцидента. При большом количестве правил/нарушений это может существенно снизить throughput и привести к росту lag. Нужны метрики времени обработки события/точки и нагрузочный тест с большим количеством нарушений, а не только обычными значениями.

### P1-4. NotificationService синхронно доставляет уведомление в Kafka listener

`NotificationService.onIncident()` делает HTTP-вызовы с повторами и `Thread.sleep` внутри потока consumer. При недоступном внешнем канале один listener блокируется до `deliveryMaxAttempts * timeout + backoffs`, снижая throughput группы. В текущем DEMO канал — HTTP endpoint самого NotificationService, что подтверждает лишь тестовый цикл, а не доставку email/push. Нужны отдельные метрики latency/attempts/FAILED и документированное ограничение. Для дальнейшего развития — отдельный delivery worker/outbox или ограниченный executor.

Кроме того, после исчерпания попыток записывается `FAILED`, а повтор Kafka event не повторяет доставку, потому что `claim()` вернёт false по `source_event_id`. Это сознательная терминальная политика, но она не является гарантией eventual delivery. Должна быть ручная/автоматическая процедура retry FAILED, если этого требует сценарий.

### P1-5. Kafka consumer lag не экспортируется в Prometheus

`result.md` прямо указывает, что lag проверяется CLI. Для демонстрации восстановления после остановки storage/processing/notification lag — одна из ключевых метрик. Нужно добавить kafka-exporter или JMX exporter/эквивалент и панели по каждой consumer group/topic/partition. Без этого в Grafana нет полной наблюдаемости главного механизма backpressure.

### P1-6. Nginx — SPOF и ограниченный балансировщик

`docker-compose.yml` запускает один Nginx. При его остановке все внешние запросы прекращаются. Это нормально для single-host DEMO, но не HA. Также Nginx конфиг с DNS resolver и переменной backend — динамическое разрешение адреса сервиса, но не health-aware балансировка с `least_conn`. Нельзя утверждать, что Nginx проверяет readiness каждой реплики. Проверить фактическое распределение запросов по `$upstream_addr` при 2+ replicas.

`proxy_next_upstream ... non_idempotent` включает повтор POST после отправки запроса upstream. Повтор безопасен только при корректной сквозной идемпотентности. До исправления P0-2 есть риск дублей.

### P1-7. Один PostgreSQL и один ClickHouse — общие точки отказа

Compose содержит по одному экземпляру PostgreSQL и ClickHouse. При отказе PostgreSQL ломаются регистрация, idempotency и обработка инцидентов. При отказе ClickHouse ingestion может продолжаться через Kafka, но история недоступна и lag storage растёт. Это ожидаемые DEMO ограничения, но не HA. Не называть Compose restart policy репликацией/failover.

### P1-8. Отсутствуют измерения, достаточные для SLA/latency требований

В требованиях:
- до 5 секунд от приёма до появления в ClickHouse;
- до 10 секунд до обнаружения инцидента обычно;
- до 20 секунд на пике.

Нужны end-to-end timestamps и histogram/summary:
- ingest accepted → ClickHouse visible;
- metric sample timestamp / ingest time → incident event published;
- incident event → notification delivered;
- Kafka record timestamp → consumer processing completion.

Сейчас отчёт в основном показывает HTTP latency и ручной lag. Это не доказывает указанные end-to-end SLO.

### P1-9. ClickHouse ReplacingMergeTree и deduplication

`ORDER BY (userId, metricName, timestamp, eventId)` и `ReplacingMergeTree(insertedAt)` плюс SELECT `FINAL` могут убирать повторные строки только при совпадении полного sorting key и в пределах поведения MergeTree. Нужно проверить:
- batchUpdate ClickHouse JDBC действительно вставляет данные как ожидается;
- повторная вставка одного eventId не даёт видимых дублей при `FINAL`;
- частичная ошибка batch не приводит к неоднозначной повторной записи;
- нагрузка SELECT FINAL приемлема.
Не заявлять exactly-once: архитектура Kafka + ClickHouse здесь at-least-once с дедупликацией на уровне чтения.

### P1-10. Границы хранения/роста не определены

История метрик partitioned по дню, но нет retention/TTL. При 20k points/s это около 1.728 млрд точек в сутки; при 60k — около 5.184 млрд в сутки. Даже если целевая нагрузка учебная и не постоянная, нужен срок хранения/TTL или политика удаления/архивации, оценка объёма и проверка cardinality/размера индексов.

### P1-11. Секреты и Compose exposure

Compose публикует наружу порты PostgreSQL, ClickHouse, Kafka admin/client ports, Redis, Prometheus и Grafana. Для локального DEMO это удобно, но не следует выставлять все сервисы наружу на публичной VM. Внешним должен быть только gateway и явно необходимые административные интерфейсы с ограничением доступа. `.env` должен быть исключён из Git; `.env.example` не должен содержать реальные credentials.

## 4. Замечания по соответствию исходному ТЗ

1. В исходном `implementation.md` FR-1 требует выдавать API key при регистрации, а FR-2 говорит об отправке с API key. Реализация использует Basic username=userId/password и прямо документирует, что API key не используется. Это функциональное отклонение от ТЗ, если оно не было отдельно согласовано. Нужно сверить с актуальной презентацией/решением владельца.
2. В ТЗ batch метрик является важным механизмом; генератор пока отправляет по одной точке. Сам endpoint поддерживает список, но нагрузочный тест не использует batch.
3. ТЗ требует доказать 20k/60k points/s, а текущие отчёты показывают до 50 points/s.
4. ТЗ требует измерять поведение во время отказов и не писать «клиент ничего не заметил», если есть ошибки/latency. Документация должна отражать точные цифры и условия.
5. ТЗ требует result.md — он есть. Но в отчёте есть расхождения с текущим кодом (F5, Kafka topology и гарантии).

## 5. Что уже сделано хорошо и не нужно переписывать

- Maven multi-module и общий `pulse-contracts`.
- Разделение storage/processing/notification.
- Независимые consumer groups для `metrics` (storage и processing) и `incidents` (metric read model и notification).
- Kafka key = userId сохраняет порядок сообщений одного пользователя в рамках partition.
- Storage consumer batch ack после успешной обработки пачки — правильное направление.
- ClickHouse как хранилище time-series и PostgreSQL для транзакционных данных — разумный выбор для учебного проекта.
- Nginx перед stateless MetricService и динамическое DNS discovery — приемлемая DEMO схема.
- Есть интеграционные тесты, fault-injection сценарии и наблюдаемость Spring/Micrometer.
- Документация честно признаёт single-host ограничения production HA.

**Не нужно переписывать проект с нуля или заменять Kafka/ClickHouse/PostgreSQL.** Сначала устранить проблемы надёжности и улучшить измерения.
