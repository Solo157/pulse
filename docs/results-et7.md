# Результаты нагрузочных испытаний

## Методика

Генератор `loadgen.py` (stdlib, планировщик RPS по окнам, стабильный
Idempotency-Key на пакет) бьёт `POST /users/{id}/metrics` через nginx
одиночными событиями; интенсивность — **запросы/с** (`LOAD_RPS`). Профили:
`baseline` (плоский RPS), `step` (ступени), `burst` (фон + пик). Метрики стека —
Prometheus (`pulse_*` счётчики); проверка отсутствия потерь — COUNT по
ClickHouse; лаг — `kafka-consumer-groups.sh` по группам `storage-group`,
`processing-group`, `notification-group`. Корректная команда чтения лага:
`docker exec kafka1 /opt/kafka/bin/kafka-consumer-groups.sh --bootstrap-server
localhost:9092 --describe --all-groups` (утилиты нет в PATH — «пустая» команда
иначе молча показывает LAG=0). Образы сервисов собираются из локальных
`*/target/*.jar`: перед `docker compose build` обязателен
`mvn package -DskipTests`, иначе в контейнер попадает старый код. Стенд: один
хост (16 CPU / 31 ГБ), генератор рядом со стеком, Kafka 3 узла (два брокера +
controller-only), ClickHouse/PostgreSQL без лимитов.

## Шаг 20k→40k→60k точек/с (2026-11-08) — ИСТОРИЧЕСКИЕ

batch=100, 32 потока отправки, ступени по 60 с, без нарушений правил.

| Показатель | Значение |
|---|---|
| Отправлено / принято | 7 200 000 / **7 200 000** точек (ошибок 0, retry 0, dropped 0) |
| Интенсивность приёма (HTTP, 202 = запись в PG-очередь; семантика того кода) | все ступени выдержаны wall=60.0 с, на пике — **60 000 точек/с** |
| Латентность HTTP (p50/p95/p99/max), мс | 3.0 / 62.0 / 92.6 / 138.2 |
| Очередь генератора high-water | 368 из 400 |
| ClickHouse, финальный COUNT | **7 200 000 — ровно как принято**: потерь и необъяснимых дублей нет |
| Устойчивая доставка в Kafka (отправитель outbox) | **≈ 42 события/с ≈ 4 300 точек/с**: каждое событие подтверждается синхронным ожиданием `ack`; за прогон в очередях накапливалось до ~55 000 событий |
| Сквозной end-to-end до ClickHouse | **≈ 4 300–4 500 точек/с**; все точки в CH через 1 530 с после конца нагрузки; LAG всех групп 0 |

## Масштабирование потребителей (ограничение партиций)

Топики `metrics`/`incidents` имеют по 2 партиции, поэтому в каждой consumer
group максимум 2 активных участника. Эксперимент 2026-11-09 на нагрузке
8 000 точек/с (исторический baseline: batch-генератор; вывод о пределе
партиций от инструмента не зависит):

| Реплик storage-service | Участники группы | Партиций на участника | Лаг |
|---|---|---|---|
| 1 | 1 | 2 | 0 |
| 2 | 2 | 1 + 1 | 0 |
| 3 | 3 | 1 + 1 + **0** | 0 |

Третья реплика присоединяется к группе (`--members` показывает её с
`#PARTITIONS 0`), но параллелизма не добавляет — это ожидаемое поведение при
2 партициях, а не дефект; роль третьей копии — горячая замена при отказе
активной. Принудительно увеличивать число партиций нельзя: ключ сообщения
`userId` и порядок точек одного пользователя должны сохраниться. Если
потребуется больше параллелизма — решение по числу партиций принимает владелец
(см. `docs/decisions.md`, предложение 4 партиций `metrics`).

## Итог

- **приём** (HTTP → публикация в Kafka с ack): базовые профили 10–40 rps
  держатся без ошибок и деградации латентности (см. базовые замеры выше и
  перемерку после отката).
- потребители ограничены числом партиций топика `metrics` (см. эксперимент по
  масштабированию).
- сквозная проверка «все принятые события в ClickHouse, LAG=0» — часть прогонов
  ниже помечена историческими; актуальные прогоны на текущем коде выполняются
  методикой запросов/с.

## Сквозные задержки (end-to-end)

Конвейер публикует гистограммы: `pulse_e2e_clickhouse_visible_seconds`
(приём → видимость в ClickHouse), `pulse_e2e_incident_published_seconds`
(время точки → подтверждение публикации инцидента брокером),
`pulse_e2e_notification_sent_seconds` (публикация инцидента → SENT) и
`pulse_event_age_seconds{consumer=…}` (возраст события на входе каждой группы).
Метки ограничены: идентификаторы пользователей и событий в них нет.

Замеры 2026-11-09, baseline 10 пакетов/с × 100 точек (1000 точек/с), 0.1 %
нарушающих точек:

| Требование | Замер p99 |
|---|---|
| данные видны в истории ≤ 5 с | **1.53 с** |
| инцидент обнаружен ≤ 10 с (обычный режим) | **1.63 с** |
| инцидент обнаружен ≤ 10 с (шаг 20k точек/с) | **1.79 с** |
| доставка уведомления (incident → SENT) | **0.98 с** |
| возраст событий на входе групп (p95) | ≤ **1.33 с** |

Пропускная способность доставки ограничена публикацией из запроса с синхронным ack;
ограничение принято оператором (решение 2026-11-09, `docs/decisions.md`)

## Как повторить

```bash
LOAD_EMAIL=<уникальный> LOAD_PASSWORD=<8+> LOAD_PROFILE=baseline LOAD_RPS=10 \
./loadgen.py
```

Параметры: `LOAD_RPS`, `LOAD_DURATION`, `LOAD_USERS` (параллельные воркеры),
`LOAD_PROFILE=baseline|step|burst`, `LOAD_STEP_MULTS` (через запятую),
`LOAD_STEP_SECONDS`, `LOAD_BURST_MULT`, `LOAD_BURST_SECONDS`, `LOAD_OUT`
(JSON-отчёт). Ступени: `LOAD_PROFILE=step LOAD_STEP_MULTS=1,2,4
LOAD_DURATION=180`; бу́рст: `LOAD_BURST_MULT=5 LOAD_BURST_SECONDS=20`.
Масштабирование под нагрузкой: `docker compose up -d --scale
metric-service=2 --scale storage-service=2 --scale processing-service=2` и
обратно в 1.

## Ограничения

Единый хост: генератор и система делят CPU, абсолютные значения латентности не
переносятся на чистый стенд. Профили step/burst без профиля нарушений не
проверяют обработку инцидентов под нагрузкой — это отдельный прогон. Истори-
ческие блоки (точки/с, дренаж очереди, outbox) оставлены как evidence состояния
кода на 2026-11-08/09 и не воспроизводимы текущим инструментом.
