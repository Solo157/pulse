# Результаты нагрузочных испытаний (Этап 7, переизмерено в точках метрик — P0-3)

## Методика (с P0-3)

`loadgen.py` измеряет **интенсивность в точках метрик**, а не в HTTP-запросах:
payload содержит `LOAD_BATCH_SIZE` точек, целевая интенсивность задаётся
`LOAD_TARGET_POINTS_PER_SEC` и однозначно даёт HTTP RPS = target/batch.
В отчёте раздельны offered load (planned), принятая отдача (accepted по ответам
202) и подтверждённая персистентность (сверка COUNT по ClickHouse + LAG Kafka).
Idempotency-Key стабилен на логический batch и его сетевые retry. Очередь работ
ограничена, переполнение считается (`dropped_jobs`), молча не теряется ничего.

Лаг Kafka читается `kafka-consumer-groups.sh` **в единицах сообщений**: при
batch=100 одно сообщение = 100 точек. Корректная команда для стенда:
`docker exec kafka1 /opt/kafka/bin/kafka-consumer-groups.sh --bootstrap-server
localhost:9092 --describe --all-groups` (скрипт лежит в `/opt/kafka/bin`, в PATH
его нет — «пустая» команда с `| awk` иначе врёт про LAG=0).

Стенд: один хост (16 CPU / 31 ГБ), генератор рядом со стеком, Kafka 3 брокера.

## Переизмерение (2026-11-08, код после P0-1/P0-2): step, batch=100, 32 потока

Ступени 20 000 → 40 000 → 60 000 точек/с (200 → 400 → 600 HTTP RPS) по 60 с,
профиль без нарушений правил.

| Показатель | Значение |
|---|---|
| Отправлено / принято | 7 200 000 / **7 200 000** точек (ошибок 0, retry 0, dropped 0) |
| Целевая интенсивность приёма | все 3 ступени выдержаны wall=60.0 с; HTTP-ingest (202 = устойчивая запись в outbox PostgreSQL) **держит 60 000 точек/с** |
| Латентность HTTP (p50/p95/p99/max), мс | 3.0 / 62.0 / 92.6 / 138.2 |
| Очередь генератора high-water | 368 из 400 |
| ClickHouse: финальный COUNT | **7 200 000 — ровно как принято**: потерь и необъяснимых дублей нет |
| Устойчивая доставка в Kafka (отправитель outbox) | **≈ 42 события/с ≈ 4 300 точек/с** — отправитель подтверждает каждое событие синхронного ожидания ack; за время замера в очередях накопилось до ~55 000 событий |
| Сквозной end-to-end до ClickHouse | все точки в CH через **1 530 с** после конца нагрузки; суммарная устойчивая пропускная способность конвейера **≈ 4 300–4 500 точек/с**; LAG по всем группам 0 |

## Вывод (честный)

После рефакторинга отказоустойчивости (P0-1/P0-2) картина стенда:

1. **Приём** (HTTP → PostgreSQL outbox) держит **60 000 точек/с** без единой
   ошибки — это и есть гарантия 202.
2. **Дальше конвейер сужается**: единственное узкое место — однострочный
   синхронный (per-event `ack`) отправитель outbox метрик, ≈ 4.3k точек/с.
   Хранение (storage→ClickHouse) успевает за ним в реальном времени (LAG≈0).
3. Сквозная персистентность стенда: **≈ 4.5k точек/с**, до 20k/60k — не хватает
   порядка величины. Причина — конфигурация/реализация отправителя, а не
   «мощность VM»; кандидат на исправление (P1-10: конвейерная пакетная
   публикация с групповым ack вместо синхронной per-event).

Заявлять «60 000 точек/с» для этого стенда корректно **только про участок
приёма**. Прежний замер 60k «сквозь» на build до P0-2 был потерей по буферу
продюсера (неdurably) и недостоверен как гарантия.

## Прежние замеры (2026-11-07), единицы — HTTP RPS (≈1 точка/запрос)

Методика была в запросах: «50 rps» означало ≈ 50 точек/с. Как измерение RPS
корректны, как points/s — вводить в заблуждение; сохранены для истории.

| Профиль | Нагрузка | Отправлено | Ошибок | p50/p95, мс | Итог |
|---|---|---:|---:|---|---|
| baseline | 10 rps, 60 с | 600 | 0 | 7.9 / 10.1 | обработано всё |
| step | 10→20→40 rps ×60 с | 4 190 | 0 | 5.1 / 7.1 | латентность плоская при ×4 |
| burst | 10 rps + пик 50 rps (20 с) | 1 396 | 0 | 4.4 / 5.8 | пик переварен |
| scale под нагрузкой | burst 50 rps, up→down | 3 157 | 32 (≈1 %) | 5.2 / 18.8 | потерь нет; 32 ошибки — обрыв keep-alive к scale-down реплике |

## Как повторить

```bash
# ступени 20k→40k→60k точек/с (атрибутировано по пользователю)
LOAD_PROFILE=step LOAD_BATCH_SIZE=100 LOAD_TARGET_POINTS_PER_SEC=20000 \
LOAD_STEP_MULTS=1,2,3 LOAD_STEP_SECONDS=60 LOAD_USERS=32 \
LOAD_EMAIL=step-$(date +%s)@pulse.dev LOAD_PASSWORD=<8+> \
LOAD_CH_COUNT_CMD="docker exec clickhouse clickhouse-client --query \"SELECT count() FROM pulse.metric_points WHERE userId='{user}'\"" \
LOAD_KAFKA_LAG_CMD='docker exec kafka1 /opt/kafka/bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 --describe --all-groups 2>/dev/null | awk "NR>1 && NF>=6 && \$6!=\"-\" {lag+=\$6} END {print lag+0}"' \
python3 loadgen.py
```

Параметры: `LOAD_BATCH_SIZE` (1..100), `LOAD_TARGET_POINTS_PER_SEC` | `LOAD_RPS`,
`LOAD_DURATION`, `LOAD_USERS`, `LOAD_PROFILE=baseline|step|burst`,
`LOAD_STEP_MULTS`, `LOAD_BURST_MULT/SECONDS`, `LOAD_VIOLATION_SHARE` (доля точек
с превышением порога правил), `LOAD_HTTP_RETRIES`, `LOAD_DRAIN_TIMEOUT`,
`LOAD_CH_COUNT_CMD`/`LOAD_KAFKA_LAG_CMD` (плейсхолдер `{user}`), `LOAD_OUT`.

## Ограничения

Единый хост: генератор и система делят CPU, абсолютная латентность не
переносится на чистый стенд. `LOAD_DRAIN_TIMEOUT` по умолчанию 300 с — при
нагрузке выше пропускной способности потребителей дренаж не успевает
(в этом прогоне не успел: фиксируется `drain_complete=false`, итоговый COUNT —
отдельным замером после дренажа). Профиль step без `LOAD_VIOLATION_SHARE` не
проверяет обработку инцидентов под нагрузкой — это отдельный прогон.
