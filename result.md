# Итоговый отчёт (result.md)

Проект: **Pulse** — конвейер телеметрии: приём метрик, инциденты, уведомления
(учебный проект по нагрузке и отказоустойчивости). Как запускать и настраивать
стенд — в README.md («Быстрый старт» и разделы про `.env`/профили); там же
сквозной сценарий. Кратко: собрать `mvn clean install` (интеграционным тестам
нужен Docker), поднять `docker compose up -d`.

## Что построено (по этапам `implementation.md`)

| Этап | Результат |
|---|---|
| 0–1 Анализ и основа | требования, архитектура (README), стенд одной командой compose, формат событий между сервисами (с версией схемы) |
| 2 Приём и хранение | `metric-service`: приём пакетов с защитой от повторной отправки и входом по паролю; `storage-service`: пачки из Kafka → ClickHouse; сквозные тесты |
| 3 Обработка и инциденты | `processing-service`: сравнение с порогами, инциденты в PostgreSQL, событие в топик `incidents`; точки пользователя идут по порядку |
| 4 Уведомления | `notification-service`: доставка в демонстрационный канал, статусы `SENT`/`FAILED`, повторные попытки, защита от повторной отправки |
| 5 Выдача данных владельцу | история метрик и инцидентов только владельцу (ClickHouse + PostgreSQL), 401/403 при чужих учётных данных |
| 6 Мониторинг | метрики всех 4 сервисов в Prometheus (новые реплики находят через DNS), дашборд «Pulse» в Grafana (показатели работы и состояния машин) |
| 7 Нагрузка и копирование | генератор `loadgen.py` (три профиля), замеры в `docs/results-et7.md`, добавление/убирание копий под нагрузкой |
| 8 Отказы | 7 сценариев F1–F7 с результатами в `docs/fault-injection.md`, шаги — `scripts/chaos.sh` |

## Качество

- Модульные и интеграционные тесты (Testcontainers): **30 из 30 зелёные**,
  `mvn clean install` — успешно.
- Общий стиль кода: русские комментарии и Javadoc у каждого класса, единообразные
  имена и слои (controller → service → repository), единый формат ответов-ошибок.
- Проверка перед каждым финальным прогоном: полная сборка, все тесты, запуск
  стенда с нуля и сквозной сценарий из README.

## Нагрузка (см. `docs/results-et7.md`)

baseline 10 запросов/с: 600 запросов, 0 ошибок, 95 % ответов быстрее 10 мс;
ступени 10→20→40: 4190 запросов, 0 ошибок, время ответа не изменилось при росте
вчетверо; пик 50 запросов/с: 0 ошибок. Добавление и убирание копий сервиса под
пиком: при остановке копии часть соединений обрывалась (32 ошибки из 3157, ~1 %),
лагов Kafka не осталось, **потерь нет** (принято ровно столько точек, сколько
лежит в ClickHouse). Лечится повтором POST другим адресом — включено настройкой
nginx `proxy_next_upstream ... non_idempotent`.

## Отказы (см. `docs/fault-injection.md`)

Убивали (docker kill) реплику metric-service — 0 ошибок; остановка любого из
трёх обработчиков — клиент ничего не замечает, очередь Kafka нарастает (~800
сообщений) и разбирается за ~23 с после запуска, ни одно сообщение не потеряно.
Остановка ClickHouse — приём метрик жив, выдача истории сразу отвечает 503
(после закрытой находки №1; раньше запрос зависал). Остановка PostgreSQL —
страдают все запросы к данным (в ней пользователи, правила и инциденты).
Убивали брокер Kafka (две копии, ждать от обеих) — приём отвечает 503
`NOT_ENOUGH_REPLICAS`, но
отправляющая сторона сама догоняет не отправленное после возврата брокера:
503 клиенту ещё не означает потерю данных.

## Находки и план развития

1. ~~Чтение не отказывало мгновенно~~ — **закрыто**: ограничитель времени
   (TimeLimiter) и выключатель отказов (CircuitBreaker `chRead`/`pgRead`) в
   `UserReadService`; ответ 503 за ~1 с при недоступном хранилище метрик,
   ~100 мс, когда выключатель уже взведён
   (`docs/decisions.md`, `ReadFailFastIntegrationTest`).
2. Потолком параллельной обработки остаются партиции топика `metrics` (сейчас 2):
   больше двух потребителей на топик не встанет — для прода нужно больше партиций и RF≥3.
3. Лаги Kafka в Prometheus не выведены (читаются только консольной утилитой);
   добавить kafka-exporter.
4. Redis под быстрый слой защиты от повторов развёрнут, но в коде не задействован.
5. Ответ 503 при недоступном брокере стоит дополнить заголовком `Retry-After`
   (сейчас отдаётся обычный 503 без подсказки, когда повторять).
6. При уменьшении числа реплик nginx не дожидается завершения активных запросов
   к убираемому контейнеру — спасает только повтор запроса (retry в nginx).

## Программа исправлений (fix-instructions)

- **P0-1 — потеря события инцидента при сбое Kafka. Закрыто.** Переход
  state-машины и событие `IncidentDetected` теперь фиксируются одной транзакцией:
  событие пишется в таблицу-очередь `metric.incident_outbox`, а отдельный
  отправитель добирает её после сбоя (пауза повтора удваивается, отправка с
  ожиданием `ack`, повтор отдаёт байт-в-байт то же событие со стабильным
  `eventId`; `eventId` больше не генерируется заново при каждой отправке).
  Обработчик пакета (`IncidentEvaluator.process`) — одна транзакция БД: при
  ошибке откатывается и состояние, и очередь, Kafka доставит пакет заново без
  задвоения. Метрики глубины и задержки очереди — в Prometheus.
  Проверено тестами: `OutboxFailurePersistenceTest` (Kafka недоступна: переход
  зафиксирован, событие в очереди, неудачные попытки не теряют запись и не
  плодят вторую), `OutboxDeliveryIntegrationTest` (отправленный payload
  идентичен записанному, повторная порция пуста, очередь переживает перезапуск
  сервиса, 4 параллельных отправителя публикуют 8 записей ровно по разу),
  существующий `IncidentProcessingIntegrationTest` идёт через outbox без
  изменений ожиданий. Метрики: `pulse.processing.outbox.*` (`docs/decisions.md`).

- **P0-2 — потеря/задвоение события ingest при неопределённом итоге
  публикации. Закрыто.** Приём пакета — одна транзакция PostgreSQL: запись
  журнала идемпотентности (с заранее выданным eventId, числом точек и отпечатком
  тела) и сам `MetricEvent` в очереди `metric.ingest_outbox` создаются вместе;
  202 теперь означает «устойчиво принято», недоступная Kafka задерживает
  доставку, но не отменяет приём (503 — только за неисправный PostgreSQL).
  Повтор того же ключа и тела отдаёт прежний ответ на любом статусе; повтор с
  другим телом — 409. Отправитель добирает очередь в Kafka с удваивающейся
  паузой, закрывает очередь и журнал одной транзакцией, а сверка статусов
  не оставляет вечно незавершённых приёмов после падения ровно после ack.
  Хранение: очереди 7 сут, журнала 30 сут. Проверено тестами:
  `MetricKafkaUnavailableTest` (202 при мёртвой Kafka, повтор — тот же eventId),
  `IngestOutboxIntegrationTest` (ack задержка/повтор без второго события;
  очереди переживают перезапуск процесса; статус догоняется сверкой; 4
  одновременных запроса одним ключом — одна операция), обновлённый
  `MetricIngestIntegrationTest`; весь модуль 26/26 тестов зелёные
  (включая прежний набор), полный реактор — зелёный. Метрики:
  `pulse.ingest.outbox.*` (`docs/decisions.md`).

- **P0-3 — измерение нагрузки в точках метрик вместо запросов. Закрыто.**
  `loadgen.py` переписан: `LOAD_BATCH_SIZE` точек в payload, цель
  `LOAD_TARGET_POINTS_PER_SEC` (HTTP RPS выводится строго target/batch),
  offered/accepted/подтверждённые персистентность раздельны; ограниченная
  очередь работ с high-water mark и `dropped_jobs`, `join()` до фактической
  отправки; стабильный Idempotency-Key на batch и его retry; проверочные
  команды (`LOAD_CH_COUNT_CMD`/`LOAD_KAFKA_LAG_CMD`) с обязательной проверкой
  кода возврата. Ступень 20k→40k→60k точек/с (batch=100): ingest и Kafka
  принимают **60 000 точек/с** без ошибок (p99 84 мс, 0 потерь); сквозная
  персистентность ограничена потребителями — ClickHouse дозаписан ≈ за 9 минут
  (storage ≈6.5k точек/с), очередь processing разобрана ≈ за 36 минут
  (≈3–3.5k точек/с); финальный COUNT ровно 7 200 000 = принято (ни потерь,
  ни дублей). Заявка «20k/60k точек/с» подтверждена только для приёма;
  для сквозных значений нужно масштабирование storage/processing
  (`docs/results-et7.md`, `docs/decisions.md`).

## Runbook

```bash
docker compose --profile obs up -d         # полный стенд (приложение + мониторинг)
curl -X POST localhost/auth/register -H 'Content-Type: application/json' \
     -d '{"email":"u@pulse.dev","password":"Passw0rd!!"}'                  # -> userId
curl -X POST localhost/users/<userId>/metrics -H "Authorization: Basic $(echo -n <userId>:Passw0rd!! | base64)" \
     -H 'Idempotency-Key: demo-1' -H 'Content-Type: application/json' \
     -d '{"metrics":[{"name":"temperature","value":91.0,"timestamp":"2026-11-07T09:01:00Z"}]}'  # -> 202
curl "localhost/users/<userId>/metrics" -u "<userId>:Passw0rd!!"            # история
curl "localhost/users/<userId>/incidents" -u "<userId>:Passw0rd!!"          # инциденты -> OPEN + notification SENT

./loadgen.py                                  # baseline-профиль (env LOAD_*)
./scripts/chaos.sh                            # воспроизведение сценариев отказа (шаги в файле)
docker compose down -v                        # полный сброс (чистые тома Kafka/PG/CH)
mvn clean install                             # тесты
```

Ограничения стенда: единый хост 16 CPU (генератор и система разделяют CPU);
`min.insync.replicas=2` при RF2 — компромисс latency/доступности для учебной
мишени. Абсолютные значения латентности не переносятся на чистый прод-стенд.
