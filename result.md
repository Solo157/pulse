# Итоговый отчёт (result.md)

Проект: **Pulse** — конвейер телеметрии: приём метрик, инциденты, уведомления
(учебный проект по нагрузке и отказоустойчивости). Как запускать и настраивать
стенд — в README.md («Быстрый старт» и разделы про `.env`/профили); там же
сквозной сценарий. Кратко: собрать `mvn clean install` (интеграционным тестам
нужен Docker), поднять `docker compose up -d`.

## Нагрузка (см. `docs/results-et7.md`)

Интенсивность измеряется в точках метрик: ступени 20k→40k→60k точек/с
(HTTP-пакеты по 100 точек, batch=100). Приём выдерживает **60 000 точек/с**
без единой ошибки (p99 ~93 мс): 202 означает устойчивую запись пакета в
PostgreSQL (журнал идемпотентности + очередь доставки); дальше конвейер
сужается — устойчивая доставка в Kafka и запись в ClickHouse ≈ 4.5k точек/с.
Профиль выдерживается без потерь и дублей: все 7.2 млн точек дошли до
ClickHouse COUNT-в-COUNT. Добавление/убирание копий сервисов под нагрузкой
настроек nginx и повтором запросов переносится без потерь. Статичные 2 копии
metric-service получают запросы поровну (замер через access-лог nginx:
802/799 из 1600), при уменьшении 2→1 под нагрузкой — 0 ошибок клиента:
заходы на снимаемый адрес (502) nginx повторяет на живую реплику.

## Отказы (см. `docs/fault-injection.md`)

Убийство реплики metric-service (`kill -9`) под нагрузкой — 0 ошибок клиента
(повтор запроса через nginx и стабильный Idempotency-Key). Остановка любого
потребителя Kafka (storage/processing/notification) — приём работает штатно,
очередь нарастает и после запуска разбирается в ноль, ничего не теряется.
Остановка ClickHouse — приём метрик работает штатно (202), выдача истории
отвечает 503 не дольше ~3 с (TimeLimiter + CircuitBreaker). Отказ брокера
Kafka — приём продолжает отвечать 202: пакет устойчиво записан в очередь
outbox PostgreSQL и доставляется в Kafka после восстановления брокера (без
потерь и дублей). Остановка PostgreSQL — деградируют все запросы к данным
(в ней пользователи, журнал идемпотентности, правила и инциденты); Kafka и
ClickHouse продолжают работать.

## План развития

1. Потолком параллельной обработки остаются партиции топика `metrics` (сейчас 2):
   больше двух потребителей на топик не встанет — для прода нужно больше партиций и RF≥3.
2. nginx DEMO — единственный экземпляр (единая точка входа, SPOF стенда) и
   узнаёт реплики только через DNS Docker: это не проверка готовности
   приложения — при уменьшении числа реплиок часть запросов первым заходом
   попадает на мёртвый адрес (замер: 163 захода 502 за прогон), спасает
   повтор nginx на живой адрес плюс журнал идемпотентности сервисов (клиент
   не увидел ни одной ошибки). Для прода — вычитанные health-проверки
   балансировщика или несколько nginx за VIP.
3. Пропускная способность устойчивой доставки (отправитель outbox метрик) —
   ≈ 4.3k точек/с из-за синхронного подтверждения каждого события; нужна
   конвейерная пакетная публикация (`docs/results-et7.md`).
4. Redis под быстрый слой защиты от повторов развёрнут, но в коде не задействован.


## Runbook

```bash
docker compose --profile obs up -d         # полный стенд (приложение + мониторинг)
curl -X POST localhost/auth/register -H 'Content-Type: application/json' \
     -d '{"email":"u@pulse.dev","password":"Passw0rd!!"}'                  # -> userId
curl -X POST localhost/users/<userId>/metrics -H "Authorization: Basic $(echo -n <userId>:Passw0rd!! | base64)" \
     -H 'Idempotency-Key: demo-1' -H 'Content-Type: application/json' \
     -d '{"metrics":[{"name":"temperature","value":91.0,"timestamp":"2026-11-07T09:01:00Z"}]}'  # -> 202
curl "localhost/users/<userId>/metrics" -u "<userId>:Passw0rd!!"            # история
curl "localhost/users/<userId>/incidents" -u "<userId>:Passw0rd!!"          # инциденты -> OPEN + notification SENT

./loadgen.py                                  # baseline-профиль (env LOAD_*)
./scripts/chaos.sh                            # воспроизведение сценариев отказа (шаги в файле)
docker compose down -v                        # полный сброс (чистые тома Kafka/PG/CH)
mvn clean install                             # тесты
```

Ограничения стенда: единый хост 16 CPU (генератор и система разделяют CPU);
`min.insync.replicas=2` при RF2 — компромисс latency/доступности для учебной
мишени. Абсолютные значения латентности не переносятся на чистый прод-стенд.
